# Phase 3 — Notification Listener Proof of Concept

## Purpose

Implement the Phase 3 notification behavior through a documented, permission-compatible Windows API. The entire in-app experience must be English, with friendly, conversational microcopy that stays clear and respectful. On first launch, GlassIsland briefly explains why notification access is needed and requests Windows permission. After permission is granted, it displays supported notifications exposed by Windows from any app, including notifications already present and notifications arriving while GlassIsland is running. Windows permission is the consent gate; do not add a second in-app opt-in that silently blocks notification display. Runtime access has not yet been proven.

## Current application constraints

- GlassIsland is a WPF desktop app targeting `net8.0-windows10.0.19041.0`.
- The current CI workflow publishes a self-contained Windows x64 executable; it does not currently establish an MSIX package identity.
- The existing product/security requirements prohibit bypassing Windows privacy controls, reading private notification stores, and logging notification content.

## API assessment

### Candidate: `Windows.UI.Notifications.Management.UserNotificationListener`

Microsoft documents this API for reading and managing notifications, including notifications generated by other apps. The documented flow is:

1. Declare the `userNotificationListener` capability in the app package manifest.
2. Explain the reason for access to the user, then call `RequestAccessAsync` from the UI thread.
3. Handle `Allowed`, `Denied`, and `Unspecified`; re-check `GetAccessStatus()` because permission can later be revoked in Windows Settings.
4. Enumerate supported app toast notifications with `GetNotificationsAsync(NotificationKinds.Toast)` and observe notification changes so existing and newly arriving notifications from any app are reflected in GlassIsland.
5. Treat empty results as ambiguous unless access status is checked: an empty collection may mean no notifications or that access is no longer available.

Official references:
- [Notification listener — Microsoft Learn](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/app-notifications/notification-listener)
- [UserNotificationListener API reference — Microsoft Learn](https://learn.microsoft.com/en-us/uwp/api/windows.ui.notifications.management.usernotificationlistener)
- [App capability declarations — Microsoft Learn](https://learn.microsoft.com/en-us/windows/apps/develop/security/app-capability-declarations)

### Important distinction

The Windows App SDK `Microsoft.Windows.AppNotifications` APIs primarily let GlassIsland **send its own app notifications**; they are not a substitute for reading notifications from other applications. The listener API is the relevant candidate for the intended feature.

## Implementation status and packaging gate

A first code-level implementation now exists: `NotificationService` requests Windows access when the API reports `Unspecified`, enumerates supported toast notifications, listens for foreground notification changes, and exposes app name, timestamp, title, and body to the WPF UI. The expanded island includes a scrollable notification list. User-facing app text has been standardized on English with a friendly, conversational voice.

The documented listener flow requires the `userNotificationListener` capability in an app package manifest and explicit user permission. The current self-contained EXE artifact alone does not declare that package capability. Therefore, this code is not yet a working end-to-end feature: the unpackaged app may fail before Windows can show its permission prompt. A package-identity test route and real Windows validation remain mandatory.

The next step is to follow the separate [Phase 3 package-identity test runbook](PHASE-3-PACKAGE-IDENTITY-TEST.md). It uses Microsoft's WinApp CLI guidance as a test route, and explicitly requires a disposable checkout because project initialization may change the target framework or project configuration. Do not add packaging machinery to the normal build until the identity-enabled run and install flow has been verified on Windows.

## Privacy and scope rules

- No notification text, title, one-time code, or message body in logs, exceptions, telemetry, or crash diagnostics.
- Do not persist notification contents. Keep any proof-of-concept data in memory and only as long as needed to validate the API.
- After Windows permission is granted, show the notification information that the API exposes and Windows makes available, including app name, timestamp, title, and body where present. Do not add a second in-app permission gate that prevents notification display.
- All user-facing strings, accessibility labels, tray menu items, errors, and empty states must be English. Prefer friendly, natural copy such as “All set”, “Nothing playing right now”, and “Your notifications will show up here”. Avoid slang that obscures permission or failure states.
- Do not dismiss or clear notifications in the proof-of-concept; that is destructive and not needed to prove read access.
- If access is denied, revoked, unsupported, or unavailable, leave the shell operational and report a clear non-repeating status.
- Never scrape private notification databases, inject into other processes, or bypass permission controls.

## Runtime validation matrix

| Scenario | Expected result |
|---|---|
| First run, access not yet decided | In friendly English, explain why access is needed, then request Windows permission on the UI thread; do not read/display notification content before permission is granted |
| User allows access | Access status is Allowed; enumerate and display supported existing toast notifications from all apps, then reflect incoming changes |
| User denies access | Clear unavailable/permission-required state; no retry loop |
| User later revokes access | Detect/check status and stop exposing notification data |
| No notifications exist | Empty state, not an exception or fabricated content |
| A notification is added/dismissed | Listener change is handled without crashing; additions/removals are reflected in the UI and UI work is dispatched correctly |
| Notification has missing or malformed fields | Safe bounded fallback; no raw content logged |
| App exits during a callback | Event handlers and resources are released |
| Package capability or API is unsupported | Explicit unavailable state; shell and media/audio continue working |

## Exit criteria

- [ ] A Windows-installed test package declares the capability correctly.
- [ ] On first launch, Windows permission is requested and the result is handled correctly.
- [ ] Existing supported notifications from all apps and incoming notifications are displayed after access is granted.
- [ ] Real runtime results are recorded for allowed, denied, revoked, and empty states.
- [ ] Notification change handling and shutdown cleanup are verified.
- [ ] Automated tests cover permission-state mapping, fallback behavior, and data minimization where practical.
- [ ] The exact supported Windows/package configuration and limitations are documented.
- [ ] No notification content is logged or persisted.

## Decision

**Do not claim notification access is working until the packaged runtime proof passes.** The listener adapter and notification list are implemented, but the feature remains unverified. Build a package that declares the required capability and verify the permission flow and notifications on Windows before marking Phase 3 complete. If the runtime test fails or distribution constraints make this access model unsuitable, revisit the feature scope. The product-facing language must remain English and conversational throughout.
